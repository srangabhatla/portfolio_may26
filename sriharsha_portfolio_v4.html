How I decide what to build · the four gates
Real problem. Asymmetric solution. Shippable in a constrained window. Valuable in one use. Every build clears all four or doesn't get built — not because I'm disciplined, but because the gates are the only honest way to know if a thing deserves to exist.

Day work · global travel-tech · Fareportal · 2023 → present
01
Built the Flight Search Decision Manager — the system that protects an OTA's quota with its supplier APIs.
In NDC, every supplier API enforces a strict Look-to-Book and Offers-to-Book ratio. Cross the threshold and the supplier cuts you off. Built a TTL-based no-result cache backed by Mongo, plus a human-curated airline route registry — together deciding which supplier APIs to hit per search. Owned the lifecycle end-to-end: discovery, PRDs, architecture, rollout, ongoing tuning.
The value shape: drastic reduction in zero-result searches, faster response times (fewer wasted API calls), better conversions, and supplier relationships that stayed inside their thresholds. The expensive problem was bleeding silently in the back-end — not on any user-facing page.
Zero-to-one Systems Backend Architecture Supplier Economics Shipped · In production
+
The frustration
In the NDC world, every supplier API charges a quota in searches, not just bookings — Look-to-Book and Offers-to-Book ratios are hard ceilings, and crossing them means the supplier cuts off the OTA. The route list per airline is dynamic and not reliably public. Some suppliers share airline profiles but skip operating-day data — so a search runs, returns nothing, and still counts against the quota. Every wasted search was the OTA bleeding money for nothing.
What I almost built
A fully automated route registry that trusted supplier profile feeds end-to-end. Faster to ship, less coordination overhead, looked clean on paper. I rejected this. The supplier feeds were unreliable — operating-day data was missing or stale on multiple suppliers — and trusting them blindly would have rebuilt the same quota-bleeding problem with extra steps. Automation without verification was the wrong primitive for this domain.
What I built instead
Two systems, working together. Part one: a Mongo-backed no-result cache, keyed on the search signature, with a per-supplier TTL. When a user search returned no itinerary, the key got pushed to the pool — and any matching subsequent search was short-circuited before it cost quota. Applied uniformly across every supplier API. Part two: an Airline Routes API that pulled supplier profile data automatically but ran every update through human validation before going live — a human-in-the-loop registry the routing layer could trust. Together: when a user searches, the backend now decides which APIs to hit based on which suppliers actually fly that route on that day, while staying inside every supplier's quota.
The trade-off
A TTL means the system briefly doesn't know a route has come back online. For the duration of the TTL window, there's a small risk of missing a real opportunity. I traded perfect coverage for quota preservation — and tuned the TTL per-supplier based on how volatile their route schedules actually were. The honest call: a route that just resumed is a small loss; an OTA cut off by a supplier is an existential one.
What I refused to add
A fully-automated, no-human registry. A "manual override" surface for agents to force searches that the system had cached as no-result. A configurable quota-bypass setting. All of them sounded helpful. All of them would have created exactly the failure modes the system was built to prevent. The discipline was the product. The moment a human can override the routing layer, the routing layer stops protecting the quota.
The lineage
Working on this taught me something I keep coming back to: the most expensive problem is rarely the one users complain about — it's the one bleeding silently in the back-end. PMs who only listen to the user surface miss it. Several of the tools in Tier 2 — especially the ones that refuse to add escape hatches users ask for — trace directly to this lesson.
Roadmap · what's next
Where I'd take this: dynamic per-supplier TTL tuning (currently coarse, could be informed by observed route-volatility), and a feedback loop where the registry's confidence per route gets scored and surfaced in routing decisions. The ceiling on this system is high — the floor was just "stop bleeding quota on routes the airline doesn't fly today."

+
The frustration
Every new supplier integration felt like a one-off. Engineering rebuilt the same scaffolding. Ops chased the same signoffs. Suppliers asked the same questions. The work was repeatable, but it wasn't being treated as repeatable.
What I almost built
More integration capacity — i.e., advocate for headcount. Easier to win, harder to defend two quarters later. I rejected it. Hiring more people to do the same wasteful work isn't a solution; it's the same problem at higher cost.
What I built instead
A streamlined backend workflow that turned the integration into a process rather than a project. Standardized the supplier-side checklist, the engineering-side mappings, the ops-side approvals. Every integration after the third one took noticeably less time.
The trade-off
The first three integrations after the redesign took longer than they would have under the old way — because the new workflow was being stress-tested on real launches. Took the short-term hit to compress every future supplier cycle. Slower three. Faster everything after that.
Roadmap · what's next
Where I'd take this: the natural extension is making large parts of supplier onboarding self-serve — push the standardized checklist out to the supplier, let them complete most of it before engineering gets involved. The goal isn't fewer suppliers; it's a system where adding one barely costs anything.

01
PM Studio — the PM-toolkit problem.
Seventeen tools for the actual PM workflow — problem framing, user-story generation, retrospective synthesis. One environment, one voice, no tab-switching.
What it gives you: the workflow compression of not switching apps. Every PM move you make daily, in one keystroke, in one place.
Phase 01 · Toolkit Product Live
+
The frustration
PM work is fragmented across six tools. Notion for notes, Jira for tickets, Figma for sketches, ChatGPT for drafting, Excel for sizing, Slack for everything else. Each switch is a context-loss. The job that should take 20 focused minutes takes a fragmented hour.
What I almost built
Yet another "AI for PMs" wrapper — chatbox in, document out. Rejected because most of those products solve "how do I write faster" and the actual problem is "how do I think more clearly without losing context."
What I built instead
A single workspace with seventeen modes that share state. Each mode is a sharply scoped PM task. The voice and structure stay consistent so the cognitive cost of switching modes is near-zero.
The trade-off
More upfront design work to make seventeen modes feel like one product. Easier path would have been one mode shipped well; instead I optimized for not making the user think about which mode they're in.
What I refused to add
Persistent project history. Multi-user collaboration. Integrations with Jira/Notion. Each one would have looked like a feature; each one would have meant a slower core experience for the solo PM working at midnight.
Lineage · taught me toolkits create choice paralysis — informed every Phase 02 build
Roadmap · what's next
Where I'd take this: shrink it. The lesson was that even seventeen scoped modes is too many. PM Studio v2, if it exists, is probably five modes that do what seventeen do today — through better defaults and sharper prompts.

Phase 01 · Toolkit Product Live
+
The frustration
Every PM has typed "## Background" at the top of a Notion doc and stalled. The hard work is in the structure, not the writing. The first draft of every PRD is essentially the same skeleton — and yet every PM rebuilds it from scratch every time.
What I almost built
A template library. Pick a template, fill in blanks. Rejected because templates are still empty pages with worse formatting. The cognitive load of "which template do I use" is its own friction.
What I built instead
A single input — describe the feature in one sentence — and a generation that produces background, problem, success criteria, user stories, edge cases, and a task hierarchy. The user reviews and shapes; doesn't draft from zero.
The trade-off
Less control over format. The output isn't infinitely customizable — it's opinionated. The bet was that "good and immediate" beats "perfect and slow" for nine out of ten PRDs.
What I refused to add
A "regenerate this section" button. Looked helpful, would have trained users to fish for output until it matched what they had in mind — defeating the point of having the system propose structure.
Lineage · the "no regenerate button" pattern carried into every Phase 02 and 03 build
Roadmap · what's next
Where I'd take this: JIRA push. Most PMs reformat the output once it's drafted — straight push to a JIRA project (with the hierarchy preserved) is the obvious next leap. After that, learning the user's organizational vocabulary so each PRD reads in their company's voice, not a generic PM voice.
One field. One sentence. Notice no template picker — choosing a template is the friction the tool was built to eliminate.
Full structure on first generation. No "expand this section" buttons. The system commits to a structure the user can edit.

Phase 02 · Single-purpose Communication Live
+
The frustration
Half of professional communication is decoding. "Could we revisit this approach" means reject. "Interesting" means kill it. Most people draft a sincere reply to the surface text and miss the actual signal entirely.
What I almost built
A "rewrite this politely" tool. The market is full of those and they all miss the point — the issue isn't writing; it's reading. Rejected.
What I built instead
A two-step tool: decode first (what is this person actually saying?), respond second (three options across registers — agreeing, pushing back, deflecting). The decode step is the entire product.
The trade-off
Forces the user to read a small analysis before they get the replies. Most "AI tools" optimize away that pause. I made the pause the feature. If you don't see what was actually said, the reply doesn't matter.
What I refused to add
A "skip to replies" button. Tone customization. Saved drafts. Each one would have shifted the product from understanding tool back to writing tool.
Lineage · proved that making the user pause is sometimes the product
Roadmap · what's next
Where I'd take this: conversation-aware decoding. Most feedback is the third message in a six-message thread; the decoding gets sharper if it can see the thread, not just the latest line.
Decode is shown first. The user has to read what was actually said before they get the replies — this ordering is the design.
Three replies, three registers. Not "polite version" / "casual version" — agreement, pushback, deflection. The choice is strategic, not tonal.

Phase 02 · Single-purpose Legal Live
+
The frustration
Most people scroll past contract language because it's exhausting. The contract assumes you'll either skip it or pay a lawyer. The middle ground — understand it well enough to push back — doesn't exist for most people.
What I built instead
Three layers of output: a plain-English summary, a flagged list of risky clauses, and concrete suggestions for what to negotiate. The user can read at the depth they want.

A "negotiate for me" button that drafts the counter-email. That would have crossed from helps you understand into acts on your behalf — different liability shape, different product.
Roadmap · what's next
Where I'd take this: contract-vs-contract diff (compare an offered contract against a saved baseline) and clause-by-clause risk scoring tuned to the user's role. A vendor reads the same contract very differently than a freelancer.
Single upload. No setup. No account creation, no clause-type picker — the user shouldn't have to know what they're looking for.
Flags before summary. Most readers want to know what's wrong before they read what's there. Inverted the conventional order on purpose.

Phase 02 · Single-purpose Research Live
+
The frustration
Researchers write for peer reviewers; practitioners need actionable insight. The translation step is invisible work that happens in someone's head — usually badly, because the practitioner skims and pulls the wrong takeaway.
What I built instead
Six configurable lenses (methodology, novelty, application, limitations, etc.) at three depths (sentence, paragraph, page). The user picks the lens that matches the question they're trying to answer.

Three depths in one view. Sentence for the scan, paragraph for the read, page for the reference — the reader chooses speed, the tool doesn't choose for them.

Phase 03 · Decision-forcing Reasoning Live
+
The frustration
You walk into the meeting having rehearsed your side. Then someone makes the obvious counter and you stall. The counter wasn't even hard — you just hadn't said it out loud to yourself.

The steelman is shown first. Most "debate" tools rebut. This one builds the opposite case before the user is allowed to defend.
Failure modes named. The tool tells you specifically which of your moves was weak — not just whether you "won."

Input the work (description, screenshots, code, whatever you have). Output is a post in your voice, framed around what the work actually represents rather than how impressive it sounds. Forces a single angle per post — no multi-thread sprawl.

Reversals · what I changed my mind about

I'm not fixated on the vision.
I'm willing to be wrong out loud.

Most portfolios show only the things that worked. I think a record of the things I changed my mind about is the most honest signal of how I actually think. Three reversals — each one was a real conviction at the time, each one cost me something to undo, each one made the work that came after stronger.

01
I used to think · distribution was a separate skill I'd acquire later
I was wrong. Distribution is part of the build.
Builders ship things and then ship nothing about them, because writing the post feels like a separate job. I lived that pattern for two years. The reversal — that distribution and craft are the same skill — became the seed for SignalPost.
+
What I believed
If the work is good enough, it'll find its audience. Spending energy on the post about the work felt like cheating — like compensating for a weak product with marketing.
What changed it
Watching multiple genuinely-good builds I'd shipped get zero traction next to mediocre ones with a sharp post attached. The work was real; the distribution was the missing piece. The post wasn't compensation — it was the act of making the work legible.
What I do now
Treat the post as part of the build. Same craft, same care. SignalPost was built directly from this reversal — to make distribution feel like the natural ending of the build instead of a separate task you forget to do.
02
I used to think · more options means more value
I was wrong. Options without forcing functions create paralysis.
PM Studio shipped with seventeen modes. Users opened it and didn't know where to start. The data taught me that giving the user choice, in this category, was hostility dressed as flexibility. Every Phase 02 build was a correction.
+
What I believed
A toolkit is more powerful than a single tool. The PM-Studio-style multi-mode environment seemed strictly better — more capability, same price.
What changed it
My own usage. I'd open my own tool, look at the mode picker, and feel the same friction a new user would. The choice of which mode to use was a decision tax I'd built into my own workflow.
What I do now
Phase 02 onward, every tool does one thing. No menu. No mode picker. The user opens the URL and is already in. Sometimes I add capabilities later — but only when the use case proves it earned the addition.
03
I used to think · my job was to give the user what they asked for
I was wrong. My job is to give the user what the work needs.
Early builds had every "regenerate", "skip this step", "show me the answer" button users asked for. I was being responsive. I was also draining the product of the friction that made it work. Senior product judgment is knowing when "no" is the right answer.
+
What I believed
Listen to the user. Add what they ask for. The user-centric mindset was supposed to be unconditional.
What changed it
Adding "regenerate" buttons to FeedbackTranslator turned a product about understanding into a product about fishing for the reply you wanted. The user got more output. The work got worse. I'd given them what they asked for and lost the thing that made the tool useful.
What I do now
Default to no when the user is asking for something that protects them from doing the work the product is meant to make them do. The user's surface request is data. Their underlying need is the brief. Sometimes those are the same. Sometimes they're not.

Manager README · Personal Operating System

How I actually work.
Not the LinkedIn version.

No corporate version. No curated arc. This is how I operate — what I believe, what drives me, what I won't do, and why I show up the way I do. Long because it's honest. Skim if you want; the page won't mind.

i.
The opening — I learned this from cricket, not from books.

You know what's strange about cricket? It's the only sport where you can dominate completely and still lose. The person with the highest average might not be the person who wins the match. Individual brilliance means nothing if the team doesn't show up.

That's leadership. That's product. That's most things, actually.

A good start that doesn't finish is just a good start. Nobody celebrates the innings if the team loses.

So I stay until the work actually lands. Not for credit. Because well begun is half done — the other half is why I'm still here.

ii.
Who I am — before the work, underneath it.

I'm trying to be a good human, a good citizen, a good son. Everything I build comes from that wholeness — not from a drive to optimize a career.

Tony Stark says "I am Iron Man" not because he's the hero. Because he's taking responsibility. Loki gets to something deeper: "I know what kind of god I want to become." Not what others told him to be. A god of his own choosing.

I make products that change how people work. I show up calm when things are melting. I build things meant to outlast the quarter and the metric. But more than any of that — I get to choose what kind of person I become. Every single day. So do you. That's the deal.

iii.
What actually drives me — obsession, not motivation.

Products are sidekicks. They solve problems. Make life better.

What really drives me is something stranger — obsession that compounds into excellence. Virat Kohli was dropped from the Indian team. Most people would have quit. He obsessed instead. Watched film. Trained harder. Came back and never left.

That's not dedication. That's obsession. And obsession is what wins when talent is lazy.

I'd take an obsessed B-player over a talented A-player who's bored. Every time. Obsession compounds. Talent doesn't.

I want to be remembered because the work mattered, the people around me got better, and I showed up fully. Not because of a title.

iv.
My values — Batman, not Joker.

Clarity and discipline, not chaos and deception. I don't hide. I don't sugarcoat. I don't say one thing and do another. When I see a problem I name it. When I mess up I own it. Honest teams move faster.

MS Dhoni in the 2019 World Cup semi-final. India is chasing. The match is slipping. Everyone is panicked. MS walks in, doesn't panic, doesn't play recklessly — just plays the next ball like it matters.

That's chosen presence. When I say yes I mean it. When things get hard I'm the last one standing. Not as a savior. As someone who refuses to let the team carry the weight alone.

v.
How I think about product — every interaction is a frame.

I've watched Baahubali fifteen times. Every viewing I notice something new about how Rajamouli constructed meaning. He didn't become a master by being talented — he became a master by being obsessed with how a frame makes you feel.

Imtiaz Ali does the same thing in Tamasha and Rockstar — every scene is layered for the person who feels too much and thinks too much at the same time. Red Dead Redemption 2 does it too. None of these things present themselves to you. They pull you in.

The vision should be so clear that even a janitor knows what film is being made. — Rajamouli

That's how I think about product. If the team doesn't understand why we're building this, we've already failed. Every interaction, every word, every animation compounds meaning. Craft is the foundation of everything else.

vi.
How I actually lead — your work, your call.

You own your work. Not me. You.

You decide how. You're accountable for the result. You get the credit when it works. My job is to be clear about why, remove blockers, make space for the work, and learn from losses without blame.

Brainstorms: real-time, back and forth, messy. Execution: async, build, ship, iterate. Stuck: talk to me immediately, don't sit on it. Feedback: I give it to you straight, sometimes wrapped in sarcasm, always from the belief that you can do better. You give me honesty, effort, growth, and respect. You get a partner who has your back.

vii.
What I won't do — the brain-rot work.

I genuinely dislike the brain-rot work of doing obvious, monotonous things just because they're expected. More importantly — when I can already see the answer clearly, spending energy persuading others to begin or chasing people for status updates feels like betrayal of the actual work.

I'd rather build the thing than sell the idea of building it. I'd rather ship what's needed than schedule a meeting to discuss whether to ship it.

This isn't laziness. It's a refusal to mistake performance for progress.

viii.
My stance on failure — three kinds, three responses.

In cricket, a batsman can be LBW playing the perfect shot. Failure is just expensive learning, and learning is how you become who you want to be.

Failure from trying: celebrated. That's how you get better.
Failure from negligence: understood, fixed, moved on.
Failure from not caring: a different conversation.

I optimize for the first. The second teaches us. The third means we're not aligned.

ix.
Living the contradictions — holding two true things at once.

I'm obsessed but I'll pivot if the data says so. The vision is clear but I'm not married to it. I plan meticulously but I stay open to breakthroughs that come from nowhere.

The work matters deeply. And I'm light about life because we're not curing cancer here — we're building products. I care about people. And I'm intense about excellence. I'm approachable. And I'm direct. Intensity without warmth is just tyranny. Warmth without intensity is just nice. I'm betting on both.

x.
A small note — the film.

Years ago I acted in a short film called Rainbow — played a young man and his friend, the same actor in two roles, in a story about figuring out your own orientation when the people around you seem so much more certain about theirs. It's on YouTube. It later won a national award.

Written and directed by Kartik Akella. Co-written by Srinivas Rao. Additional dialogue by Sampath Ganesh. I mention it not to flex — I mention it because every reference I reach for when I describe how I want things to feel is cinema. Imtiaz Ali. Rajamouli. RDR2. The film is where that started.

xi.
What I actually want to be known for — that I gave a damn.

That I showed up.
That I made the people around me better.
That the work mattered.
That I wasn't full of it.
That I helped people see they had agency.

I'll be gone. You'll be gone. The opportunity stays. I just don't want to be the one who missed it.

p.s.
One last thing.

I'm not perfect. I'm learning. Some days I'm better at this than others. But I always try, I always own my mistakes, and I always show up.

If you've read this far, you already know whether we should talk.

Things I've noticed, written down, or can't stop thinking about. Not a content strategy — just a mind processing the work it moves through. A long-form build story sits at the bottom.

Behavior · Observation
The most capable people often don't act — not because they can't.
It's organizational signal failure. When the environment consistently tells people their actions won't change outcomes, they stop acting — regardless of capability. The problem isn't motivation. It's the signal. This is the insight a behavioral nudge tool I'm prototyping is trying to solve.
Product · AI
Prompts are products. Most people haven't realized that yet.
A prompt isn't an instruction. It's a product decision. It has a user, a job to be done, edge cases, and a failure mode. The PMs who internalize this first will build things the others can't picture. I've been thinking about this since before it became a LinkedIn topic.
Cricket · Leadership
Why a great innings doesn't matter if the team loses.
Cricket is the only sport where you can dominate completely and still lose. Most performance reviews optimize for the innings, not the result. The honest evaluation is whether the thing actually landed.
Decision-making · Patterns
Convergence is harder than discovery — and almost no tool helps with it.
There are a hundred apps for generating ideas. Almost none for picking one and committing. The real bottleneck for most people isn't options — it's the inability to collapse messy input into a single direction.
Product · Distribution
Your work already happened. Now let it work.
Most builders treat distribution as a separate skill they need to acquire later. The honest move is to treat the post about the work as part of the work. Same voice, same craft, lower stakes. The work doing two jobs at once.
Comics · Systems
Why I'm building a production pipeline instead of just drawing panels.
The bottleneck in original IP isn't creativity — it's production. If the pipeline works, the story scales. If it doesn't, the best scripts in the world stay scripts on a hard drive.
Career · Pattern
Generalist isn't a category. It's a posture.
The label "generalist" gets thrown at anyone who's worked across domains. But there's a real difference between someone who happens to have done many things, and someone whose operating system is to step into ambiguity, frame the problem, and ship. The first is a résumé. The second is a way of working.
AI · Workflow
The 5x rule — most AI tools fail it.
A useful AI tool has to be at least five times faster, cheaper, or better than the manual alternative. Anything less and the friction of switching kills adoption. Most "AI features" added to existing products fail this test silently.
Process · Honest take
PM is mostly translation work. Nobody admits this.
Engineers say one thing, the business says another, users say a third, and the PM's actual job is to hold all three in their head and ship something that honors all of them. The output is a roadmap. The work is translation.
